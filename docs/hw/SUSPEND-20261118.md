# Suspend investigation, flo, 2026-11-18

## Observed state

- Booted kernel: `7.2.0-postmarketos-qcom-apq8064`, package revision r48.
- `/sys/power/state`: `freeze mem`; `/sys/power/mem_sleep`: `[s2idle]`. There is no `deep` platform suspend mode, so logind's Suspend request can enter only suspend-to-idle.
- RTC wakeup is enabled. Battery was 98–99% and charging during these tests.
- `pm_test=freezer` followed by `freeze` completed and incremented `suspend_stats/success` to 1.
- `pm_test=devices` followed by `freeze` failed twice with `-EBUSY` at `4300000.gpu`; `suspend_stats/fail` reached 2. The second attempt was with the shell locked and display blanked, so visible rendering is not sufficient to explain the failure. The original `pm_test=[none]` setting was restored after each attempt.
- The kernel reported `adreno 4300000.gpu: PM: dpm_run_callback(): platform_pm_suspend returns -16` and `failed to suspend: error -16`. Wi-Fi briefly deauthenticated during the device test and reconnected after resume.

## Driver path and hypothesis

The r48 source archive `cc2a6a249989c3bb23d3191afb97bf60f01d535f` has `adreno_system_suspend()` waiting for `active_submits == 0`, then calling `pm_runtime_force_suspend()`. The A3xx callback calls `a3xx_idle()` and then `a3xx_vbif_halt()`. A ring-drain or RBBM idle timeout logs an error; neither was in the device log. The VBIF halt path returns `-EBUSY` without logging its request or acknowledgment. **The VBIF acknowledgment timeout is therefore the leading hypothesis, not yet a demonstrated root cause.**

The six-bit request mask was added upstream to drain VBIF before A3xx GPU suspend. A later upstream fix narrows the mask for A306/A306A, but Flo has A320; changing its mask without measuring the request and acknowledgment would be speculative. See the [upstream A3xx driver](https://kernel.googlesource.com/pub/scm/linux/kernel/git/torvalds/linux/+/master/drivers/gpu/drm/msm/adreno/a3xx_gpu.c), [original VBIF drain patch](https://lore-kernel.gnuweeb.org/phone-devel/20260610-mainline-fix-a3xx-gpu-hang-sending-v1-1-9282182840b5%40alex-min.fr/T/), and [A306 mask discussion](https://lists.openwall.net/linux-kernel/2026/10/16/1026).

The r49 diagnostic package is built locally from the r48 source with a
single patch that logs the VBIF halt request and acknowledgment on timeout.
It was installed offline on 2026-11-19; the upgrade simulation and actual
transaction changed only the kernel package. The boot files in `/boot` and
the lk2nd partition were compared byte for byte after the upgrade. r49 then
booted; `greetd` and NetworkManager are
active, and Wi-Fi reconnected. Its SHA-256 is
`194d2ce47afe6164b798ccc95af122597c5b50273427f7faa26ad0d3eb31f968`.
The packaged kernel configuration and Flo device tree match r48 byte for byte.
Both r48 boot

## r49 results and next evidence

The r49 `pm_test=devices` failed with `-EBUSY` twice: once with the greeter
display active and once with its DPMS off. Both failures logged
`request=0x0 ack=0x0 mask=0x3f` from `a3xx_vbif_halt()`. The diagnostic
patch captures the request immediately after writing it, before polling;
the zero readback does not identify whether this register reads back on
Flo or why the acknowledgment stays zero. The second attempt restored
DPMS on. After both tests `pm_test=[none]`; `greetd` and NetworkManager
remained active, Wi-Fi reconnected, and the battery still reported Full.

A subsequent kernel trace recorded the GPU's bus suspend callback failing
with `-16` after about one second. No GPU clock enable/disable event appears
between the start of device suspend and that callback. This does not prove
the VBIF register block was accessible throughout. The raw trace is retained
locally at `build/nexus7-r49-suspend-trace-20261119.txt`.

The next diagnostic source is committed as `058fe3b63` on
`linux-flo/flo/suspend-diagnostics-r50`; its pmaports recipe is `ee98f8f`
on `flo/suspend-diagnostics-r50`. It adds no suspend behavior change:
only on timeout it logs `needs_hw_init`, RBBM status and VBIF clock state.
The patch applied without fuzz to the pinned source archive, checkpatch
reported zero errors and warnings, and the A3xx object compiled for ARM.
The full r50 APK has not been built or installed: host `sudo` authentication
timed out while awaiting the user's fingerprint.

Both r49 boot copies were compared byte for byte and archived on the host
before any r50 deployment. The archive
`build/nexus7-r49-boot-both-20261119.tar` contains the kernel, initramfs,
Flo DTB and extlinux configuration from `/boot` and lk2nd; SHA-256
`31473e0cf574c5fec8b2ec8041128ca6456664ef20bb68a0670e6a45ec0da1ab`.
The lk2nd partition was unmounted after the read-only backup.

1. Build r50 after host authentication and measure GPU initialization, RBBM status and VBIF clock state at the timeout.
2. Change the driver only after these values identify the failure. The A306 three-bit mask is not evidence for an A320 change.
3. Repeat the device test twice with no suspend failures or GPU hangs. Then arm the RTC and make one short logind Suspend request with the operator nearby to wake with Power if needed.
4. Confirm greeter/PIN, touch, Wi-Fi, charging, and the active session after resume. Measure whether s2idle actually reduces idle power; a successful transition alone does not establish useful battery life, especially with `cpuidle.off=1`.

The [kernel PM test procedure](https://www.kernel.org/doc/html/next/power/basic-pm-debugging.html) recommends progressing from freezer to devices before a real suspend. The [kernel sleep-state documentation](https://cdn.kernel.org/doc/html/latest/admin-guide/pm/sleep-states.html) distinguishes s2idle from deep suspend. Keep the shell using logind's Suspend method; it already locks the session before requesting sleep.
